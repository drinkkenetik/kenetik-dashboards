## Incident

- Mobile site CVR **3.34% → 2.14%** (material drift, RED). Homepage is the #1 landing page.
- Homepage script errors **~10 → ~130 per 1,000 sessions** over four days.
- Sessions down (not up) → on-site break, not a tracking artifact.

## Hypothesis

Reverting the homepage hero from the re-enabled 4-slide Slick fade carousel back to a single static evergreen slide removes the autoplay/fade/clone code path that only executes with >1 slide. This eliminates the homepage script-error spike and recovers mobile CVR toward its 3.34% baseline — without restoring the out-of-stock Golden Pear hero.

## Root cause (bisected)

Bisected every change to `drinkkenetik/kenetik-shopify-theme` over the last 10 days. The **only** file touching the homepage is `templates/index.json`, edited **Mon 6/15 20:38** via the Shopify customizer (committed as a `shopify[bot]` sync). That edit:

- set `disabled: true` on the single-slide **Golden Pear** hero (`new_hp_banner_D3rgVe`, button → `pages/golden-pear`) — the OOS swap, and
- re-enabled the legacy **4-slide** hero `new_hp_banner_tHDgpj` (blocks: `banner_Thm7tc`, `banner_KdUmiW`, `banner_hgACUj`, `banner_zzHLM4`).

That hero runs a Slick carousel via `assets/cw-custom.js`:
`$('.home-banner-slider').slick({ autoplay:true, speed:500, fade:true, cssEase:'linear', infinite:true … })`.

Slick only starts autoplay when `slideCount > slidesToShow` (i.e. **>1 slide**), so the single Golden Pear banner kept the carousel completely inert — no autoplay, no fade transitions, no infinite clones. The 4-slide hero re-activates that whole path on every session, and it is the **only `fade:true` slider on the site**. This is the only behavioral delta and it matches the spike timing exactly.

**Ruled out:** `cw-custom.js` (init), `cw-plugins.js` (Slick lib, bundled), `sections/new-hp-banner.liquid`, its CSS, and `theme.liquid` are unchanged for months. Tuesday's `settings_data.json` edit was an unrelated `gp_cans_found 3→4` counter. Wed PR #85 touched only Norwitz/partner pages. Server-rendered HTML confirms all 4 hero images resolve (no 404s) — the regression is purely client-side JS.

**Evidence caveats (honest):** Exact live console stack not captured — drinkkenetik.com is blocked to the browser agent by org policy, and the sandbox could not install a headless browser (npm registry blocked). Root cause established via git bisect + source analysis + server-rendered HTML.

## Fix (rollback-ready, data-only)

A plain `git revert` of the 6/15 commit is **not** safe — it would bring back the OOS Golden Pear hero. Instead, trim `block_order` of `new_hp_banner_tHDgpj` to a single evergreen slide:

```diff
       "block_order": [
-        "banner_Thm7tc",
-        "banner_KdUmiW",
-        "banner_hgACUj",
-        "banner_zzHLM4"
+        "banner_Thm7tc"
       ],
```

This restores the known-good single-slide behavior that held 3.34% CVR (slide kept: "Performance Starts in the Mind" / Hero_Image_1, button → `collections/drinks`). The other 3 slides remain in `blocks{}` for instant restore once the carousel is debugged.

Delivered as PR branch **`fix/homepage-hero-single-slide-cvr`** on `drinkkenetik/kenetik-shopify-theme` (pushed). PR awaiting Katie review/merge.
