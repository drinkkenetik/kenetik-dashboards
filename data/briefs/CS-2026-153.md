# CS-2026-153 — Pre-Deadline Owner Slack-Post Hard-Gate

## §10a Hypothesis

**Claim:** Requiring CS owners to post in #kgs-team 24h before their next deadline (measurement_due, published_due, approval_due) creates an asynchronous early-warning Slack-evidence trail that surfaces decision-throughput failures earlier than tracker.json status checks alone.

**Mechanism:** S50 today observed (pat-017) that the 5/12 hard-deadline cluster (CS-138 deploy, CS-145 winback variants, CS-147 RCA, CS-148 winback pause) all carry unchanged "draft" status with **0 Slack evidence** post-5/12 across 3 evidence searches for queue-relevant terms (CS-091, huddle, decision queue, Ashton, Superfiliate, code attach, engineering lead, Polar). Tracker.json snapshots showed the symptom (status unchanged); Slack snapshots confirmed the failure mode (no owner-side communication of slip or completion). The pipeline currently has no asynchronous mechanism that forces owners to surface deadline status BEFORE the deadline passes — by then, the slip is silent and the team learns only when the dispatch DM lands the next morning.

**Pairs with:** CS-2026-152 (Team-Huddle Decision-Throughput Governance). CS-152 is the synchronous forcing function (30-min huddle resolves N parallel decisions). CS-153 is the asynchronous early-warning signal (24h-pre-deadline Slack post). Together they form a complete decision-throughput governance loop: huddle reverses accumulated queue, pre-deadline post prevents queue accumulation.

## §10b Resolution Path (Diagnose / Remove / Refine / Add)

1. **Diagnose.** Root cause of pat-017 (silent-slip pattern): the daily pipeline observes the SYMPTOM (tracker status unchanged past due date) one cycle after the failure. Owners face no asynchronous mechanism that prompts them to surface status before the deadline. CS-152 is a synchronous fix; gaps remain in the async layer.

2. **Remove.** Can we remove what's enabling silent slip? The enabling condition is "no required pre-deadline owner action visible in Slack." Removing it requires adding a required action (Step 4 below). There is no piece of the system to remove — silent slip is enabled by absence, not by presence of a bad mechanism.

3. **Refine.** Does an existing mechanism almost handle this? `changeset-lifecycle-sweep.md` Phase 4 already queues "owner-nudge" Slack DMs for stale items. The refinement is to extend Phase 4 nudges with a NEW class — "pre-deadline" — fired 24h before `measurement_due`/`published_due`/`approval_due`, addressed to the owner, AND requiring an owner reply post in #kgs-team to satisfy the nudge. Existing infra: yes. Existing nudge SLA: yes. Existing public visibility: no. **REFINE is the primary path.** The 24h-pre-deadline trigger and the public-visibility requirement are the two refinements.

4. **Add.** What new piece is necessary? One new daily-pipeline check (`pre_deadline_post_required[]` array on tracker.json entries, populated by lifecycle sweep Phase 4 when 24h-pre-deadline fires; cleared by dispatch when a satisfying Slack message is detected). The check itself is small; the refined nudge does the heavy lifting.

**Conclusion:** REFINE existing nudge infrastructure + minimal ADD (single tracker field + dispatch detection logic). Do NOT add a new role/forum/process step.
