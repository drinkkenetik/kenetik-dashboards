## §10b RESOLUTION PATH ANALYSIS

**Diagnose:** The KGS daily synthesis surfaces operational metrics (D-domain scans, recommendations, ChangeSet candidates) but does NOT systematically surface **process-automation opportunities** as a first-class output. Devon has been driving automation work for weeks, but the synthesis pipeline has no dedicated lane that captures "where would automation reduce time-per-CS by N%?" — so automation work happens despite the system, not because of it.

The skill-mix-bound bottleneck (per CS-120 restructure) means *redistribution doesn't fix* Katie's concentration — only *time-per-CS reduction* does. The KGS therefore needs to be tuned toward identifying time-per-CS reduction opportunities continuously, not as an afterthought.

**Remove:** Stop treating the daily synthesis recommendation list as a flat priority queue where automation candidates compete with execution candidates. They serve different functions — execution candidates compound business outcomes; automation candidates compound the system's own velocity.

**Refine:** Add a dedicated "Automation Opportunity Surfacing" lane to the daily synthesizer + ChangeSet recommender that:
1. Tracks per-CS time-cost (briefing time, review time, execution time, measurement time) as observable signals.
2. Identifies the highest-time-cost steps in the process and surfaces automation candidates against them.
3. Routes automation candidates to a separate weekly review (Devon + named cross-surface-data-infrastructure owner per CS-120 #1').
4. Closes the loop with a monthly retrospective: which automation investments paid back, by how much (time-per-CS delta).

**Add:** The instructions + scoring + queue mechanism above. ChangeSet template gains an optional "automation_opportunity" classification field. Synthesizer instructions gain an automation-section in the priority stack output.

**Why this earns its place:** Without it, automation work is opportunistic — it happens when Devon notices a manual step. With it, the system itself routes attention to the highest-leverage automation work continuously. The CS-120 #1' single-owner pattern + this routing mechanism are the two halves of the same fix.

## PROPOSED CHANGE

### A. Synthesizer instruction patch

Update `cgo-daily-pipeline/config/task-b-synthesis.md` (and downstream synthesis output template) to include a new section:

```
## Automation Opportunity Surfacing (NEW)

Reviewed against the time-cost signals from the prior week's CS lifecycle:
- [Top 3 highest-time-cost process steps observed this week]
- [Automation candidates against each — feasibility-scored]
- [Recommended next automation CS to spawn — with estimated time-savings]
- [Status: open / spawned as CS-XXX / scaled / not pursued]
```

This section runs after the existing § Theme stack and before the § Demand Signals block. It reads from the new time-cost signals (B below) and from the ChangeSet lifecycle history.

### B. Time-cost observability — append fields

Add three optional fields to ChangeSet schema (`changeset-common-functions.md §2`):

| Field | Type | When set | Purpose |
|---|---|---|---|
| `time_cost.briefing_minutes` | int | At /new-changeset close | How long brief authoring took |
| `time_cost.review_minutes` | int | At /changeset-review close | How long review took |
| `time_cost.execution_minutes` | int | At /changeset-execute close | How long execution took |
| `time_cost.measurement_minutes` | int | At /changeset-measurement close | How long measurement took |

These are voluntary fields; missing values are fine. The synthesizer aggregates whatever's present to surface the highest-time-cost step class (briefing vs review vs execution vs measurement) and routes automation candidates against the dominant class.

### C. ChangeSet template addition

Add an optional `automation_opportunity` section to the brief template (`new-changeset.md` § Resolution Path):

```yaml
automation_opportunity:
  identified: true | false
  process_step_targeted: briefing | review | execution | measurement | cross-surface
  estimated_time_savings_per_CS_minutes: <int>
  estimated_CSes_per_month_affected: <int>
  feasibility: high | medium | low
  blocker: <if low feasibility, what's blocking>
```

When set, the CS gets routed to the weekly automation review (D below) rather than the standard CGO copilot lane.

### D. Weekly automation review tier

15-minute weekly between Devon and the cross-surface-data-infrastructure owner (per CS-120 #1'). Reviews:
1. New `automation_opportunity` candidates from the past week's syntheses.
2. In-flight automation CSes — status, next milestone.
3. Closed automation CSes — measured time-per-CS delta.

Outputs:
- One ratified automation candidate moves to "spawn next" status.
- Existing automation work gets a status nudge.
- Closed-loop time-per-CS delta logged in a new index file (`data/process-automation/time-cost-history.json`).

### E. Monthly retrospective

End-of-month, the cross-surface-data-infrastructure owner produces a one-page retro: which automation investments paid back, by how much. Routes into the next monthly calibration ceremony per kenetik-brain SKILL.md (existing framework).

## SUPERSEDING PROPOSED CHANGE — 2026-04-29 (the actual fix)

The original § PROPOSED CHANGE block above is **superseded** by this single Refine.

### One change, one file: `cgo-daily-pipeline/config/task-b-synthesis.md` Phase 2 § Step 2

Append the following instruction block at the end of the recommendation generation step:

```
### Automation-leverage annotation pass

After the recommendation list is written, scan each `rec-XXX` for whether its
proposed change would automate, eliminate, or measurably reduce time-per-CS on
a process step (briefing, review, execution, measurement, or cross-surface
data).

For each recommendation:
1. If the change targets a process-step automation: append the annotation
   `[automation-leverage: high | medium | low]` to the recommendation line.
   - high: would save >2 days median per CS AND apply to >5 CSes/month
   - medium: would save 1-2 days per CS OR apply to 2-5 CSes/month
   - low: would save <1 day per CS or apply to <2 CSes/month
2. Compute the savings estimate by reading tracker.json timestamps for closed
   CSes in the same `category` and class:
   - briefing_duration = routed_date - created
   - review_duration = approved_date - routed_date
   - publish_duration = published_date - approved_date
   - measurement_duration = closed_date - published_date
   Use the median across the past 30 closed CSes in the matching cohort.
3. After the recommendation list, add a "Top automation-leverage candidates"
   mini-section listing the 1-3 highest-leverage annotations, each with the
   estimated savings and the recommended next step (typically: spawn as a CS
   with `category: system_improvement`).
4. Surface the top candidate in Devon's Layer 2 dispatch DM as a single
   line: "Top automation candidate this week: rec-XXX — estimated [N] days
   median saved per CS across [M] CSes/month."
```

That's it. **One file edited, one prompt block added, zero schema changes, zero new files, zero new meetings.**

### Routing automation CSes through existing pipeline

When Devon decides to spawn an automation CS from the surfaced candidate, use:
- `category: system_improvement` (existing enum value, 2 prior uses)
- `subtype: implementation`
- Standard `/changeset-review` flow
- Standard `/changeset-execute` flow

No new pipeline. No new review tier. No new approval surface. The candidate flows through the same machinery as every other CS.

### Closed-loop measurement (no new file needed)

When an automation CS closes successfully, the synthesizer reads `tracker.json` for the next week's CSes in the matching cohort and reports the post-vs-pre median delta in the synthesis. No new state file, no new dashboard, just the existing tracker as the source of truth. If the automation paid back, the next synthesizer run shows the median dropped.
