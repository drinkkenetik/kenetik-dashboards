## §10b RESOLUTION PATH ANALYSIS

**Diagnose:** The KGS daily synthesis surfaces operational metrics (D-domain scans, recommendations, ChangeSet candidates) but does NOT systematically surface **process-automation opportunities** as a first-class output. Devon has been driving automation work for weeks, but the synthesis pipeline has no dedicated lane that captures "where would automation reduce time-per-CS by N%?" — so automation work happens despite the system, not because of it.

The skill-mix-bound bottleneck (per CS-120 restructure) means *redistribution doesn't fix* Katie's concentration — only *time-per-CS reduction* does. The KGS therefore needs to be tuned toward identifying time-per-CS reduction opportunities continuously, not as an afterthought.

**Remove:** Stop treating the daily synthesis recommendation list as a flat priority queue where automation candidates compete with execution candidates. They serve different functions — execution candidates compound business outcomes; automation candidates compound the system's own velocity.

**Refine:** Add a dedicated "Automation Opportunity Surfacing" lane to the daily synthesizer + ChangeSet recommender that:
1. Tracks per-CS time-cost (briefing time, review time, execution time, measurement time) as observable signals.
2. Identifies the highest-time-cost steps in the process and surfaces automation candidates against them.
3. Routes automation candidates to a separate weekly review (Devon + named cross-surface-data-infrastructure owner per CS-120 #1').
4. Closes the loop with a monthly retrospective: which automation investments paid back, by how much (time-per-CS delta).

**Add:** The instructions + scoring + queue mechanism above. ChangeSet template gains an optional "automation_opportunity" classification field. Synthesizer instructions gain an automation-section in the priority stack output.

**Why this earns its place:** Without it, automation work is opportunistic — it happens when Devon notices a manual step. With it, the system itself routes attention to the highest-leverage automation work continuously. The CS-120 #1' single-owner pattern + this routing mechanism are the two halves of the same fix.

## Re-Audit 2 — Awareness Depth — 2026-04-29 (Devon scrutiny round 2)

**Trigger:** Devon's second scrutiny: *"In the task b prompt block add... is a scan of each rec-XXX really enough to find automation leverage? I feel like this will take more awareness of and reasoning about the functionality of the system itself and what current capabilities and processes are."*

**He's right.** The prior simplified prompt ("scan each rec for automation leverage") treats automation as a *tactical filter* on this week's recommendations. But the recs the synthesizer generates are tactical work items ("ship CS-098", "reactivate creator BETTER", "fix the TT ingestion gap") — they don't surface *structural* automation opportunities like "review process takes 3 days median because Phase 2 anti-pattern check requires manual library lookup." That kind of opportunity only appears when the synthesizer reasons about **the process meta-layer** — the steps, sub-steps, capabilities, and existing infra — not about today's tactical recs.

**The Diagnose-Remove-Refine-Add audit didn't reach deep enough.** The "Refine" lever is correct (one prompt change), but the prompt's *content* needed more depth. Same surface-level fix, deeper reasoning required inside it.

### What changes in this re-audit

The simplified § SUPERSEDING PROPOSED CHANGE block above is itself **superseded** by this re-audit's prompt design. No new schema, no new files, no new meetings — those simplification gains are kept. What changes is the **reasoning depth required of the synthesizer inside the prompt**.

### The actual prompt block — process-step analysis (revised)

The existing prompt block stays in `cgo-daily-pipeline/config/task-b-synthesis.md` Phase 2 § Step 2. The text replaces the "Automation-leverage annotation pass" block with this:

```
### Process Automation Opportunity Surfacing (added 2026-04-29 per CS-2026-129)

Beyond reviewing today's recommendations, perform a process-step analysis on
every synthesis run. The goal is to surface STRUCTURAL automation opportunities
(where time accumulates inside the process itself), not tactical ones (which
the rec list already captures).

The analysis is a chain of seven sub-steps:

1. Compute median process-step duration from tracker.json timestamps for the
   past 30 closed CSes:
     briefing_duration = routed_date - created
     review_duration = approved_date - routed_date
     publish_duration = published_date - approved_date
     measurement_duration = closed_date - published_date
   Skip CSes where any required timestamp is null. Skip CSes with negative
   durations (data-quality artifacts; flag for cleanup but do not fail).

2. Identify the process step with the highest median duration. That is this
   week's automation target.

3. Read the canonical process documentation for the targeted step:
     briefing  -> kenetik-growth-system/commands/new-changeset.md
     review    -> kenetik-growth-system/commands/changeset-review.md
     execution -> kenetik-growth-system/commands/changeset-execute.md
     measurement -> kenetik-growth-system/commands/changeset-measurement.md
     cross-cutting -> kenetik-growth-system/commands/changeset-lifecycle-sweep.md
   Identify the sub-steps inside the targeted process. For each sub-step,
   classify it as one of:
     - automated_via_existing (uses an MCP / script / GHA workflow today)
     - manual_could_automate_via_existing (manual today, but capabilities exist)
     - manual_requires_new_build (manual today, no existing capability)
     - manual_unautomatable (judgment-bound, e.g., final approval decision)

4. Inventory existing capabilities by reading three lists:
     - MCPs available (from the active session's tool list)
     - scripts/ directory contents (`ls scripts/`)
     - .github/workflows/ directory contents (`ls .github/workflows/`)
     - kenetik-brain reference files (claims-compliance.md auto-checking,
       brand-voice.md auto-checking, etc.)
   Cross-reference manual sub-steps from #3 against this inventory: which
   manual sub-steps could be automated TODAY using existing infra (vs needing
   new build)?

5. Cross-check against shipped automation work to avoid re-recommending:
     read tracker.json for closed CSes where
       category in {system_improvement, infrastructure, data_infrastructure,
                    internal_infra}
       AND closed_date >= 90 days ago
     Skip any candidate that has already been built.

6. Surface the top candidate as a "Process Automation Candidate" entry with:
     - Step targeted (briefing | review | execution | measurement | cross-cutting)
     - Median time-cost (from #1)
     - Sub-step (specific name from process doc)
     - Manual-or-automated classification (from #3)
     - Existing capability that would be leveraged (from #4) OR
       "requires new build" with brief sketch
     - Feasibility: high (existing infra suffices) | medium (modest new build)
                  | low (substantial new infra required)
     - Estimated savings: median_time_saved_per_CS × CSes_per_month_affected
     - Recommended next action: typically "spawn CS with
       category=system_improvement targeting the named sub-step"

7. Tactical pass on rec-XXX list (lightweight fallback):
     For each rec, annotate with [automation-leverage: high|medium|low] if and
     only if the rec's proposed change directly automates a process step.
     Most recs will not get this annotation — that's expected; tactical recs
     are usually about today's work, not about the process.

8. If steps 1-6 find nothing meeting medium-or-higher feasibility (the system
   is well-automated this week, or the apparent bottleneck has already been
   addressed), output:
     "No new structural automation candidates this synthesis. Open backlog:
      [list closed-since-last-quarter system_improvement CSes + open ones]."
   That is a valid output — do not fabricate candidates.

Surface the top candidate in Devon's Layer 2 dispatch DM as a single line:
"Process automation candidate: [step] / [sub-step] — est. [N] days median
saved per CS across [M] CSes/month, feasibility [high|med|low]."
```

### Why this is the right depth

The prompt requires the synthesizer to:
- Look at what the system currently does (process docs)
- Look at what's already built (capabilities inventory)
- Look at where time is leaking (tracker timestamps)
- Reason about which manual sub-steps could leverage existing infra (vs needing new build)
- Avoid re-recommending shipped work (tracker filter)

That's the level of awareness Devon was pointing at. Not "scan recs" — *understand the system*.

The fallback pass on recs (step 7) keeps the tactical surface available without making it the primary mechanism. The "no new candidates" output (step 8) prevents fabrication on slow weeks.

### Cost considerations

The synthesizer does more reading per run:
- One process doc (the targeted step's command file): typically 200-800 lines, manageable
- Three directory listings: cheap
- One tracker filter for closed system_improvement CSes: cheap
- Reasoning over the inventory: O(sub-steps × capabilities) — bounded small

Net additional context: well within the synthesizer's existing scope. Phase 2 already loads many files; adding one more process doc per run is incremental.

### What this still doesn't do (honest scope)

- It does not maintain a curated automation backlog. The "current backlog" referenced in step 8 is just a tracker filter view, not a managed document. If you want a managed backlog later, that's a follow-up CS.
- It does not score whether automation work paid back. CS-129's closed-loop measurement (synthesizer reads pre-vs-post median time-per-CS) is unchanged.
- It does not recommend non-process-related infra work (e.g., dashboard improvements, data pipeline rebuilds). Those flow through the standard rec list as before.
- It does not auto-spawn CSes — Devon decides when to spawn from the surfaced candidate.

## Re-Audit 3 — Cadence + Cost + Backlog — 2026-04-29 (Devon scrutiny round 3)

**Trigger:** Devon raised three concerns:
1. *"Are you certain about the cost? It seems like a heavy lift."*
2. *"Maybe one that can / should be done once per week. More frequently is preferable, but I don't want to do this every time if it isn't going to surface new opportunities every time — I want to minimize redundant processing."*
3. *"Would these be candidates to add as recs? What is the best place to capture them? Not having a backlog of opportunities it identifies sounds like a miss."*

He's right on all three. I underestimated cost, defaulted to daily without justifying it, and proposed no persistence layer when one already exists.

### Honest cost accounting (was wrong before)

Per deep run, additional context required:
- Process doc for the targeted step: ~500 lines (changeset-review.md = 506, changeset-execute.md = 521, changeset-lifecycle-sweep.md = 920). Median ~500 lines.
- Capability inventory (3 directory listings + 3-4 brain references): ~80 lines.
- Tracker filter for closed `system_improvement` / `infrastructure` / `data_infrastructure` / `internal_infra` CSes (90d): ~50 lines.
- Reading `running-log.json → pending_recommendations` for open process_automation recs: ~30 lines.

**Total per deep run: ~660 lines / ~46K chars / ~11.5K tokens of input** + ~5K tokens reasoning overhead = **~16-19K tokens per run**.

If daily (5 weekday synthesis runs/week): ~80-95K tokens/week of *additional* synthesizer cost beyond what's already happening.
If weekly (1 run/week, Monday default): ~16-19K tokens/week. **80% reduction.**

I was wrong to call this "incremental." It's substantial — comparable to adding a small department brief read to every run. Weekly is correct.

### Cadence: weekly default + manual on-demand

The deep process-step analysis runs once per week (Monday's synthesizer pass). The other six daily runs do only the lightweight tactical rec-scan (annotate `rec-XXX` lines whose proposed change directly automates a process step — that pass is cheap, ~zero additional context cost).

For ad-hoc analysis between Mondays, Devon invokes via the existing CGO copilot lane — *"Run an automation-opportunity analysis"* — same prompt, same output, just triggered explicitly. No new command needed; the copilot already reads the same files.

### Backlog: `running-log.json → pending_recommendations` IS the right home

This file is **the existing cross-session aggregator** — 202 entries today. Schema (verified): `id, text, routed_to, created, priority`, often `updated` and `status`. Designed exactly for "carry recommendations across sessions until resolved." When a rec resolves, it's marked; new sessions read open ones to avoid re-recommendation.

Adding `category: process_automation` to that schema is additive (no breaking change — many existing entries don't have a category field at all; it's freeform-ish). The synthesizer's Phase 4 already writes back to running-log.json — wiring this in costs nothing new.

### Revised mechanism (round 3)

The patch to `cgo-daily-pipeline/config/task-b-synthesis.md` Phase 2 § Step 2 becomes a **two-pass design**:

```
### Process Automation Opportunity Surfacing (added 2026-04-29 per CS-2026-129)

Two passes, different cadences, different scopes.

#### Pass A — Lightweight tactical rec-scan (DAILY, runs every synthesis)

For each `rec-XXX` in this synthesis run, annotate with
[automation-leverage: high|medium|low] IF AND ONLY IF the rec's proposed
change directly automates a process step (e.g., "automate Klaviyo MCP
campaign-report retry on failure" or "wire phantom-dependency detection
into the lifecycle sweep"). Most recs will not get this annotation —
that's expected. Cost: ~zero, runs daily.
```

## Cadence Mechanism — Round 6 — 2026-04-29 (Devon scrutiny round 6)

**Devon's question:** *"How does the synthesizer prompt know to only run the full analysis once per week?"*

I undercommitted in round 3. The text said "Pass B: WEEKLY, runs ONLY on Monday OR manual invoke" but didn't specify enforcement. Three options exist, only one is right for our constraints.

### Three options, with honest cost/risk

| Option | Mechanism | Pros | Cons |
|---|---|---|---|
| **A. In-prompt date check** | Synthesizer reads `{{today}}` (already passed by orchestrator), computes day-of-week, conditionally runs | Zero infra change; works with existing context | Fragile — Claude has to remember the rule each run; no self-healing if Monday is missed; requires day-of-week math in a prompt |
| **B. Orchestrator-side gate** | cgo-daily-pipeline composes the synthesis prompt differently on Monday vs other days — append Pass B block on Mondays, omit on Tue-Sun | Clean separation; synthesizer just executes whatever prompt arrives | Requires changes to the orchestrator/pipeline composer (more places to touch); rigid Monday-only with no self-healing |
| **C. Self-managed via existing state** | Pass B preamble reads `running-log.json → pending_recommendations`, finds most recent open entry with `category=process_automation`, computes age. If < 7 days: skip. If ≥ 7 days or no entry: run. | No orchestrator change. Self-healing if a run is missed (Tuesday picks up Monday's miss). Cadence becomes "at least every 7 days" not rigid Monday — which is what was actually wanted. Operationally honest signal (how stale is the analysis?) not calendar-bound (is it Monday?) | Slightly more state-aware logic in the prompt; requires the prompt to have the running-log read path (already in the round 3 design for cross-check anyway) |

**Choice: Option C.** It piggybacks on the running-log read that round 3 already required (the cross-check against open `process_automation` recs). Same data, used twice — once for cadence, once for cross-check. No new file reads, no orchestrator change, no day-of-week math.

### Updated Pass B preamble (replaces the round 3 "WEEKLY Monday default" framing)

```
#### Pass B preamble — Cadence check (self-managed)

Pass B is throttled to once-per-7-days minimum to avoid redundant deep analysis.

1. Read running-log.json → pending_recommendations.
2. Find the most recent entry where:
     category == "process_automation"
     AND status not in {resolved, completed, deferred, dismissed}
   (matches both round 3's cross-check filter and this cadence check)
3. Compute age = today - max(entry.updated, entry.created) for that entry.
4. Decide:
   - age < 7 days → SKIP Pass B for this run.
     Output one line: "Process automation: deep analysis last ran [age] days
                       ago. Next deep analysis after: [today + (7-age) days]."
   - age >= 7 days OR no such entry exists → RUN Pass B (steps 1-8 below).
5. Operator override: if the current synthesizer invocation context contains
   an explicit "run automation analysis" or "force Pass B" instruction (e.g.,
   from a direct synthesizer re-run by Devon), bypass the cadence check and
   run Pass B regardless. Log the override in the rec entry's notes field.
```

### Why "at least every 7 days" beats "Mondays only"

- **Self-healing.** If Monday's pipeline run fails or is delayed, Tuesday's run sees age=8d and picks up the work. With Option B, Tuesday's run would just say "skip — not Monday" and we'd wait until next Monday.
- **Operationally honest.** The signal is "how long since we did this analysis" — that's the actual concern. Day-of-week is a proxy.
- **Cheap.** The state read is already happening for cross-check. Adding the age computation is two lines of logic.
- **No orchestrator dependency.** Round 6 doesn't require any change to cgo-daily-pipeline composer logic. The synthesizer reads its own state and decides.
- **Manual invoke is clean.** Operator override is just a phrase in the prompt context. No need for a separate command surface (which is good — we just deleted /cgo-copilot, so there isn't one).
